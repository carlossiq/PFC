1. RESUMO EXECUTIVO
================================================================================

Este projeto implementa um sistema completo de prospecção tecnológica que integra
múltiplas APIs de dados (OPS para patentes, Scopus para artigos científicos) com
um sistema de geração automática de relatórios utilizando LLM (Large Language
Model) local via Ollama e tecnologia RAG (Retrieval-Augmented Generation).

O sistema foi desenvolvido com foco em:
- Consolidação de dados heterogêneos de múltiplas fontes
- Geração de relatórios estruturados no padrão REPTEC/AGITEC
- Processamento local de dados (sem envio para servidores externos)
- Modularidade e extensibilidade
- Rastreamento detalhado de custos de API e uso de tokens

================================================================================
2. CONTEXTO E OBJETIVOS
================================================================================

2.1 PROBLEMA ABORDADO

Organizações que realizam pesquisa de tecnologias emergentes enfrentam desafios:
- Necessidade de consolidar dados de múltiplas fontes (patentes, artigos)
- Análise manual consome tempo e recursos
- Relatórios padrão REPTEC/AGITEC exigem estrutura específica
- Falta de ferramenta integrada que combine busca + análise + geração

2.2 SOLUÇÃO PROPOSTA

Sistema integrado que:
1. Busca patentes no OPS (Espacenet - European Patent Office)
2. Busca artigos científicos no Scopus
3. Consolida dados em formato unificado
4. Gera relatórios estruturados via LLM local
5. Rastreia custos e performance

2.3 OBJETIVOS ESPECÍFICOS

Objetivo Geral:
- Criar plataforma web para análise e geração automática de relatórios de
  prospecção tecnológica

Objetivos Específicos:
1. Implementar integração com APIs OPS e Scopus
2. Desenvolver sistema de consolidação de dados heterogêneos
3. Criar pipeline de geração de relatórios com LLM local
4. Implementar RAG para contexto inteligente
5. Rastrear tokens, custos e performance
6. Documentar sistema para produção

4. APIS UTILIZADAS

4.1 OPS (ESPACENET - EUROPEAN PATENT OFFICE)

Propósito: Busca de patentes internacionais

Endpoint: https://ops.espacenet.com/3.2/rest-services/

Autenticação:
- Username: Conta OPS
- Password: Token de acesso
- Tipo: HTTP Basic Auth

Funcionalidades Implementadas:
1. Search by CQL (Common Query Language)
   - Busca em campos: título, resumo, aplicantes, inventores
   - Filtros por data, classificação (CPC/IPC)
   - Limite: 2000 resultados por busca

2. Document Retrieval
   - Obtenção de metadados completos
   - Resumos e abstracts
   - Informações de aplicantes e inventores
   - Classificações tecnológicas

Query Builder (OPS):
- Arquivo: services/query_builders/ops_query_builder.py
- Método: Constrói queries CQL válidas a partir de termos extraídos
- Exemplo:
  (ti = ("machine learning" OR "deep learning")) AND
  (ab = ("healthcare")) AND
  (pd >= 20180101 AND pd <= 20261231)

Limitações:
- 2000 resultados por busca
- Rate limiting: ~100 requisições/segundo
- Requer conta registrada

Dados Extraídos:
- publication_number (identificador único)
- title (título da patente)
- abstract (resumo técnico)
- applicants (lista de depositantes)
- inventors (lista de inventores)
- cpc_codes (classificações CPC)
- ipc_codes (classificações IPC)
- year (ano de publicação)
- legal_status (status legal)

4.2 SCOPUS (ELSEVIER)

Propósito: Busca de artigos científicos e publicações

Endpoint: https://api.elsevier.com/content/search/scopus

Autenticação:
- API Key: Token de acesso fornecido por Elsevier
- Tipo: Header-based authentication

Funcionalidades Implementadas:
1. Simple Search
   - Busca por palavras-chave
   - Filtros por ano, área de estudo
   - Suporta operadores booleanos

2. Metadata Retrieval
   - Informações completas de artigos
   - Autores e afiliações
   - Citações e impact
   - DOI e links

Query Builder (Scopus):
- Arquivo: services/query_builders/scopus_query_builder.py
- Método: Constrói queries usando sintaxe Scopus
- Exemplo:
  TITLE-ABS-KEY(("machine learning" OR "deep learning") AND "healthcare")
  AND PUBYEAR > 2017 AND PUBYEAR < 2026

Limitações:
- Rate limiting: 9 requisições/segundo
- Máximo 5000 resultados por busca
- Requer subscription ativa

Dados Extraídos:
- title (título do artigo)
- authors (lista de autores)
- abstract (resumo)
- year (ano de publicação)
- journal_or_source (periódico/conferência)
- citations (número de citações)
- doi (Digital Object Identifier)
- keywords (palavras-chave)
- affiliations (instituições dos autores)
- field_of_study (áreas de pesquisa)

4.3 OLLAMA (LOCAL LLM)

Propósito: Geração de texto para relatórios

Endpoint: http://localhost:11434/api/

Modelos Utilizados:
1. qwen2.5:3b-instruct (geração de texto)
   - Tamanho: ~2GB
   - Parâmetros: 3 bilhões
   - Velocidade: Rápida (local)
   - Qualidade: Boa para português
   - Contexto: Até 32k tokens

2. nomic-embed-text (embeddings)
   - Tamanho: ~334MB
   - Dimensionalidade: 384
   - Velocidade: Muito rápida
   - Qualidade: Alta para RAG

Funcionalidades:
1. generate() - Geração de texto com contexto
2. generate_embedding() - Geração de embeddings para RAG
3. health_check() - Verificação de conectividade

Configuração:
- Temperatura: 0.3 (menos criatividade, mais factual)
- Top-p: 0.95 (diversidade controlada)
- Max tokens: 1500 por seção

Vantagens:
- ✅ Processamento local (privacidade)
- ✅ Sem custos de API
- ✅ Velocidade razoável
- ✅ Controle total

Desvantagens:
- ❌ Requer instalação local
- ❌ Menos capacidade que GPT-4/Claude
- ❌ Português não é força

4.4 CHROMADB (VECTOR DATABASE)

Propósito: Armazenamento e retrieval de embeddings para RAG

Endpoint: Local (armazenado em .chroma_db/)

Funcionalidades:
1. Document Storage
   - Armazena até 50 patentes + 50 artigos
   - Mantém embeddings sincronizados
   - Busca por similaridade (cosine distance)

2. Context Retrieval
   - Top-k retrieval (top 5 documentos mais similares)
   - Filtragem por tipo (patent vs article)
   - Metadata preservation

Configuração:
- Implementação: PersistentClient (nova API)
- Collection: "research_documents"
- Espaço de métrica: cosine similarity
- Persistência: Em disco (.chroma_db/)

Vantagens:
- ✅ Local (sem envio de dados)
- ✅ Integração nativa com Ollama
- ✅ Fácil de usar
- ✅ Sem custos

5. PIPELINE DE PROCESSAMENTO
================================================================================

5.1 FASES DO PIPELINE

Fase 1: REFINE TOPIC (Refinamento do Tema)
└─ Entrada: Tema bruto do usuário
└─ Processamento: IA (Gemini/Claude) refina e expande tema
└─ Saída: Tema refinado com termos-chave
└─ Rastreamento: Tokens consumidos, custos
└─ Duração típica: 2-5 segundos

Fase 2: PROBE SEARCH (Busca Exploratória)
└─ Entrada: Tema refinado
└─ Processamento:
   └─ QueryBuilder OPS: Cria query CQL
   └─ QueryBuilder Scopus: Cria query Scopus
   └─ Executa busca em paralelo (OPS + Scopus)
   └─ Limita a 100 resultados iniciais por API
└─ Saída: ~200 resultados (patentes + artigos)
└─ Métricas: Patents found, articles found
└─ Duração típica: 10-20 segundos

Fase 3: EXTRACT TERMS (Extração de Termos)
└─ Entrada: Resultados da busca exploratória
└─ Processamento:
   └─ IA extrai termos relevantes de título/resumo
   └─ Agrupa por relevância
   └─ Identifica sinônimos
└─ Saída: Lista de termos refinados (20-40 termos)
└─ Duração típica: 3-8 segundos

Fase 4: FINAL SEARCH (Busca Final)
└─ Entrada: Termos extraídos
└─ Processamento:
   └─ Reconstrói queries OPS e Scopus com termos refinados
   └─ Executa busca com termos booleanos combinados
   └─ Consolida resultados (remove duplicatas)
   └─ Limita a 2000 resultados máximo
└─ Saída: Dataset completo de patentes + artigos
└─ Métricas: Total patents, total articles, duração
└─ Duração típica: 15-30 segundos

[NOVO] Fase 5: REPORT GENERATION (Geração de Relatório)
└─ Entrada: Research object com patents + articles
└─ Processamento:
   └─ ReportDataMapper: Consolida dados
   │  └─ Agregações de patentes (por ano, aplicante, CPC)
   │  └─ Agregações de artigos (por ano, journal, field)
   │  └─ Extração de curva-S (technology lifecycle)
   │
   └─ RAG Indexing: Cria embeddings e indexa
   │  └─ 50 patentes (máximo)
   │  └─ 50 artigos (máximo)
   │  └─ Armazenado em ChromaDB
   │
   └─ Report Generation: Gera 10 seções
   │  └─ Finalidade (propósito da pesquisa)
   │  └─ Referências (contexto)
   │  └─ Objetivo (meta específica)
   │  └─ Introdução (background)
   │  └─ Metodologia (como foi feita a pesquisa)
   │  └─ Informações Científicas (dados de artigos)
   │  └─ Informações Tecnológicas (dados de patentes)
   │  └─ Tendências e Ciclo de Vida (análise prospectiva)
   │  └─ Conclusão (síntese)
   │  └─ Referências Bibliográficas (fontes)
   │
└─ Saída: Relatório Markdown (português formal REPTEC/AGITEC)
└─ Duração típica: 60-120 segundos (depende do Ollama)

6.3 AGREGAÇÕES REALIZADAS

Patentes (OPS):
- Por ano: Conta de patentes em cada ano
- Por aplicante: Top 10 depositantes (nome + contagem)
- Por CPC: Top 10 classificações CPC (muito específico à invenção)
- Por inventor: Top 10 inventores (nome + contagem)

Artigos (Scopus):
- Por ano: Conta de artigos em cada ano
- Por journal: Top 10 periódicos (nome + contagem)
- Por field: Top 10 áreas de estudo (nome + contagem)
- Por autor: Top 10 autores (nome + contagem)
- Citações: Total + média

6.4 EXTRAÇÃO DE CURVA-S (Technology Lifecycle)

A curva-S descreve o ciclo de vida de uma tecnologia:
1. EMERGING (0-5% adoção): Poucos resultados, crescimento inicial
2. GROWTH (5-50% adoção): Crescimento acelerado
3. MATURITY (50-95% adoção): Crescimento lento, estabilização
4. DECLINE (95%+ adoção): Obsolescência

Algoritmo:
1. Calcula growth_rate = (patentes_recentes - patentes_antigas) / patentes_antigas
2. Classifica fase baseado em growth_rate
3. Identifica peak_year (ano com mais patentes)
4. Retorna análise prospectiva

Exemplo:
- growth_rate > 0.2 → GROWTH (mais de 20% ao ano)
- growth_rate > 0.05 → EMERGING (5-20% ao ano)
- growth_rate > -0.05 → MATURITY (decrescimento leve)
- growth_rate < -0.05 → DECLINE (decrescimento forte)

7. SISTEMA DE RAG (RETRIEVAL-AUGMENTED GENERATION)
================================================================================

7.1 O QUE É RAG?

RAG = Retrieval-Augmented Generation

Processo:
1. RETRIEVAL: Busca documentos relevantes no vector database
2. AUGMENTATION: Adiciona documentos como contexto para o LLM
3. GENERATION: LLM gera resposta usando documentos como referência

Objetivo:
- Evitar hallucinations (invenção de dados pelo LLM)
- Fornecer contexto específico do domínio
- Citar fontes reais (patentes e artigos)

7.2 IMPLEMENTAÇÃO (RAGService)

Arquivo: services/rag_service.py
Tamanho: ~300 linhas

Componentes:

1. Text Chunking
   - Divide documentos longos em chunks de 1000 caracteres
   - Overlap de 200 caracteres para continuidade
   - Mínimo de 100 caracteres por chunk

   Exemplo:
   Documento: "Patente XYZ: Sistema de recomendação... [5000 chars]"
   Chunks:
   - Chunk 1 (0-1000): "Patente XYZ: Sistema de..."
   - Chunk 2 (800-1800): "...de recomendação..."
   - Chunk 3 (1600-2600): "...usando machine learning..."

2. Embedding Generation
   - Usa nomic-embed-text para gerar embeddings
   - Cada chunk → vetor de 384 dimensões
   - Armazenado em ChromaDB

   Exemplo:
   "Sistema de recomendação usando machine learning"
   → [0.234, -0.156, 0.889, ..., 0.123] (384 valores)

3. Similarity Search
   - Busca chunks similares usando cosine distance
   - Top-5 retrieval (retorna 5 mais similares)
   - Filtragem por tipo (patent vs article)

   Exemplo:
   Query: "machine learning in e-commerce"
   Similaridade com chunks:
   - Chunk A: 0.95 ✓ (muito similar)
   - Chunk B: 0.87 ✓ (muito similar)
   - Chunk C: 0.78 ✓ (similar)
   - Chunk D: 0.65 ✓ (moderadamente similar)
   - Chunk E: 0.52 ✓ (minimamente similar)
   - Chunk F: 0.31 ✗ (não retornado)

4. Context Building
   - Concatena chunks similares em ordem
   - Mantém metadata (source, type, year, api)
   - Injeta no prompt para o LLM

   - Força citação de fontes

   - Verifica coerência do texto gerado
   - Valida referências a documentos
   - Detecta números inventados

9. Backend gera relatório (RAG + Ollama)
   ↓
10. Frontend recebe Markdown/LaTeX
    ↓
11. Mostra editor com preview side-by-side
    ↓
12. Usuário pode editar e exportar PDF

15.5 INTEGRAÇÃO DE EDITOR E EXPORT PDF
================================================================================

FLUXO COMPLETO (COM INTERFACE WEB):

1. GERAÇÃO INICIAL
   Backend gera Markdown formatado

2. ENTREGA AO FRONTEND
   Frontend recebe Markdown e exibe em:
   - Editor (Monaco)
   - Preview (lado a lado)

3. EDIÇÃO DO USUÁRIO
   Usuário edita conteúdo no navegador:
   - Muda texto
   - Adiciona/remove seções
   - Formata em LaTeX
   - Auto-save a cada 30s

4. CONVERSÃO PARA PDF
   Quando usuário clica "Download PDF":

   Opção A: Markdown → PDF
   - Frontend envia Markdown para backend
   - Backend usa pandoc para converter
   - Retorna PDF pronto para download

   Opção B: LaTeX → PDF
   - Frontend envia LaTeX para backend
   - Backend usa pdflatex para compilar
   - Retorna PDF com qualidade superior

   Opção C: HTML → PDF (client-side)
   - Frontend renderiza Markdown em HTML
   - Usa html2pdf.js para converter
   - Sem necessidade de chamada ao backend

5. DOWNLOAD
   Usuário faz download do PDF
   - Mantém editor intacto
   - Pode fazer novos downloads após edições
   - Histórico de versões salvo

CONVERSÃO MARKDOWN → LATEX → PDF:

Sistema gerará Markdown inicial, mas usuário pode:
1. Editar Markdown no navegador
2. Sistema converte em LaTeX antes de PDF
3. Compila LaTeX para PDF final

Exemplo de Markdown → LaTeX:

MARKDOWN:
──────────
# Título da Seção

**negrito** e *itálico*

- Item 1
- Item 2

Equação: $E=mc^2$

LATEX (Convertido):
──────────────────
\section{Título da Seção}

\textbf{negrito} e \textit{itálico}

\begin{itemize}
  \item Item 1
  \item Item 2
\end{itemize}

Equação: $E=mc^2$

PDF (Compilado):
────────────────
[PDF renderizado com fontes profissionais]

16. LIMITAÇÕES E TRABALHOS FUTUROS

16.1 LIMITAÇÕES ATUAIS

⚠️ Ollama qwen2.5
  - Menos preciso que GPT-4 ou Claude
  - Português poderia ser melhorado
  - Contexto limitado (~32k tokens)
  - Mais lento que APIs remotas

⚠️ ChromaDB
  - Até 100 documentos (50 patentes + 50 artigos)
  - Índice em memória (pode usar RAM)
  - Não distribuído

⚠️ Fase de Report
  - Gera seções de forma sequencial (não paralela)
  - Cada seção toma ~8-10 segundos
  - Total: 80-100 segundos para 10 seções

⚠️ Sem integração de gráficos
  - System gera path para gráficos
  - Mas não gera os gráficos propriamente
  - Necessário integrar matplotlib/plotly
